# Kirikiri：按格式族识别、移植与验收

本页是 [Kirikiri 引擎页](../kirikiri.md) 的通用工作路线。按格式特征分派算法。先定位失败层，再扩展该层；不创建另一套按游戏命名的批处理流程。

译文回注优先走 [patch.xp3 增量补丁流程](#译文回注优先使用-patchxp3-增量补丁)。这是 Kirikiri 游戏常见的资源覆盖机制，不限于 Hxv4；具体索引、加密和挂载规则由目标游戏决定。

## 当前能力与阶段

KAG `.ks` 的 Alter `nm/np/exlink` 方言已支持对白、姓名、选项和加密封包，见 [KAG 文本工作流](kag-text.md)。其他 KAG 方言仍需语义核对，不能把词法覆盖当作全部宏可安全回填。

### SCN 派生文本与聊天消息方言

`SCN derived text mismatch` 属于已解密 PSB 的语义检查，不应通过换密钥、删除缓存校验或直接保留旧缓存绕过。当前错误会附上归档成员、scene/text/cache 位置。逐条比较正文、speech/search 缓存及长度字段，再为可解释的转换增加规则。

SCN 的 `\[文字]` 表示字面括号，不是 ruby。控制码检查保护 `\[` 与结束 `]`，括号内文字可译；长度与读音/搜索缓存按显示的 `[文字]` 重建。当前只接受无嵌套、无内嵌控制码、单行且闭合的形式，未知转义不能直接删除反斜杠或放宽全部括号检查。

已支持 ruby 注音两端全角空格的排版归一化：只在源缓存精确匹配时记录 `trim_ruby_space`，回写使用同一规则；不删除正文全角空格，也不把注音内部空格一概清除。该标志和已有 `strip_ruby_dot` 均进入 manifest，原文回写须字节一致。

无 `text` 也无 `language` 的选项只有两种已知结构可跳过：仅含非负整数 `selidx` 的标记；或至少含 `selidx`、`storage`、`target` 的链接记录（仅可额外含 `button`、`close`）。`storage` 必须精确等于所属 SCN 的 `name`；`target` 是 `*` 加 1–255 个字母/数字/下划线/点/连字符，可含日文字符但不能有空白或控制语法；`button` 是 1–32 个 ASCII 字母/数字/下划线/点/连字符；`close` 仅接受 PSB 布尔节点或字符串 `true`/`false`。空对象、空值/布尔索引、负索引、数字 close、缺失必要字段或未知字段仍拒绝。

这些结构记录与语言无关，在选择语言槽前识别，原样保留、不导出，位置和键集记入 `skipped_structural_choices`；总数包含纯结构脚本和仅含 `selidx` 的标记。带 `language` 的记录仍须验证所选显示字段，不因缺失 `text` 而自动跳过。结构记录不含文本并不说明按钮没有显示文字：图像/UI 中的文字需单独检查。

带长度的多语言 tuple 可有末尾整数零字段；它不是另一种不带长度的语言布局，尤其不能把 voice 列表误认作语言列表。单张图片消息 `[display, "%i1&资源名;", 1, alt]` 的第四项是替代文本，导出为 `image-alt`，不是语音缓存；回写只改 alt，图片引用、图元计数、voice、尾部字段保持原样。未知四项形状继续拒绝。

场景状态里的 `phonechat` 历史快照仍作为非目标结构保留，不自动根据相同字符串推断它与正文的绑定。正文/图片替代文本回写通过不等于手机 UI 历史已同步翻译；涉及该界面时须单独研究快照引用与恢复逻辑并实测。

| 层 | 已实现 | 判定条件及缺口 |
|---|---|---|
| XP3 索引 | 标准 `File`、`eliF` 名称映射、已有 `sen:` 专用适配器 | 有界索引/段解析；未知索引标签和链式变体拒绝 |
| 独立正文过滤器 | none、hash、xor、stripe、akabei、haikuo、exa、yuzu | JSON 参数；共用解包与重封包；除 none 外 7 种算法 |
| Hxv4 | [静态配置、名称核验、正文过滤和保留身份的 writer](hxv4.md) | 不启动游戏；已知 PSB SCN 使用 `kirikiri_hxv4_text` 复用共享对白契约，其余资源走归档入口 |
| Cx | 已验证的 Senren 控制块与配置 | 属于专用配置，不等于支持任意 Cx/Hxv4 |
| 内层分类 | PSB 完整有界树、BOM 文本、KAG 词法、PNG 块 CRC、TJS2 签名 | 每种验证强度单独报告；TJS2 只有签名证据 |
| SCN 语义读写 | PSB v2/v3 单语言、多语言已知 tuple | 统一 `kirikiri_extract`，包括姓名、选项、长度、缓存、非文本语义比对 |
| KAG 词法基础 | 原文区间、换行、注释、标签、命令、内联属性引号、脚本块 | `kirikiri_kag.py`；不把词法 token 当作对白 JSON |
| KAG 语义读写 | `kirikiri.py` 有限区间接口、`kirikiri_kag_text` 的 Alter 方言 | Alter `nm/np/exlink` 已接入批处理；其他宏和分组规则仍需语义适配 |
| TJS 字节码、加密内层 PSB | 未提供通用 writer | 保留诊断，继续静态格式研究，不运行游戏或解释未知代码 |

上游 [过滤器覆盖清单](../../provenance/kirikiri-filter-coverage.json) 枚举固定 GARbro-Mod 提交中 `KiriKiri/*.cs` 的全部 55 个 `ICrypt` 派生类（沿继承关系追踪），逐项区分已移植、专用配置和未移植。这是源码覆盖清单，不是“55 种都能用”，也不代表其他上游没有新算法。

## 从证据选择下一步

1. **先识别索引**。XP3 魔数和 `File` 只证明容器布局；历史 API 中 `index_profile=plain` 的含义是标准索引，不能据此断言正文是明文。`0x80000000` 标志同样不是具体密码算法的指纹。
2. **解压与过滤分层**。本文独立过滤器的顺序为分段解压 → 以整个成员的逻辑偏移过滤 → 合并 → 验证明文 Adler-32。新算法若按压缩字节过滤、修改文件头或具有跨成员状态，必须另建明确适配器，不能套这个接口。
3. **明确参数来源**。来源可以是用户提供的配置、随包已记录且适用条件明确的配置或经验证的已知明文恢复。仅靠标题近似、扩展名或一个 BOM 不足以选择参数。不要把历史游戏配置集合当作默认自动猜测表。
4. **验证候选**。至少两个不同内容成员的完整校验与内层验证支持参数候选；再在整个选中脚本集合逐项验证。候选、已解密、已解析、已语义导出、已回填、可运行必须分别报告。
5. **定位内层失败**。Adler 错误先检查过滤器、种子、段偏移、压缩阶段；Adler 正确但 PSB/KAG 解析失败时，研究脚本封装/方言，不继续盲换归档密码。`.ks` 与 `.scn` 是筛选条件，不是格式证明。
6. **只在正确层补代码**。索引变体进归档适配器，密码进过滤器注册表，文本标签语义进 KAG 方言，tuple 变体进 SCN parser。导出、manifest、回填和验证应继续复用公共流程。

## 适配新文本方言的方法

目标是确定“哪些字段显示给玩家、如何分组、修改后还要更新什么”，而不是让某个报错消失。先形成可验证的规则，再接入现有提取/回写流程。

1. **固定失败层与最小样本。** 保存源哈希、成员名、编码/版本和出错位置；取正常与异常记录各几条，覆盖旁白、姓名、选项、ruby、空记录及不同语言槽。归档校验已通过时，优先研究内层包装或语义，不继续盲换密码。全量统计结构差异，不能只修第一条异常。
2. **核对随包实现的读写边界。** 阅读本仓库对应的 parser、writer、方言说明和测试，用游戏样本确认哪些结构已经覆盖、哪些需要补齐。区分结构导出、字符串池筛选与真正对白提取；能导出 JSON 不代表已有正确的语义 writer，能读加密格式也不代表能恢复原加密外壳。缺少布局或语义依据时保留诊断，继续从样本验证假设，不放宽校验来迁就未知结构。
3. **建立字段和状态规则。** KAG 静态读取宏定义，确认姓名属性、清名时机、结束/换行标签、选择项与 ruby 写法；同名宏不能直接套用。PSB/序列化结构按关键字段类型与相邻关系识别正文、显示名、内部 ID、voice、长度、缓存和语言列表，不只凭数组总长度判断。可忽略的附加字段须有不参与文本解释的证据，并原样保留；存在歧义就继续检查，不能把“接受任意尾字段”当作通用化。
4. **列清可写字段及依赖。** 只读 ID、路径、表达式、控制码与正文分开；姓名槽、选项属性、图片替代文本分别建定位。识别语音/检索缓存、聊天历史、共享字符串和其他语言副本，证明引用关系后才同步修改，不能仅按字符串相等绑定。长度要确定是字节、UTF-16 单元、码点还是可见字数。缓存不符时解释其转换规则，不删除校验或保留过期缓存；尚未覆盖的显示路径必须报告。
5. **在正确层实现可复用适配。** 包装解码、文本词法、语义分组、归档过滤各归各层；差异用有明确含义的 profile/参数表达，不新增游戏名脚本。优先扩展共享 parser/writer；新结构无法合理共用时再拆适配器。配置不得执行代码。原文 JSON 和 manifest 保持可追溯，变体参数参与回写校验，不能临时改元数据绕过检查。
6. **按证据验收。** 先用合成样例覆盖新规则、近似但不合法的结构和旧方言；再做真实原文 parser→writer 往返、中文变长回写、重新解析及非文本结构比较，最后恢复外壳、重封包并读回。可以字节一致的原文必须一致；格式规范化导致差异时须逐项解释，不能只凭“能读回来”通过。全量所选脚本验证后，另行测试补丁挂载、存档恢复和实际显示，不能将这些阶段合并宣称成功。

适配完成只补对应引擎文档、算法出处和必要回归：说明识别条件、支持的显示字段、尚未覆盖的路径及下一步。失败报告应指向成员和具体字段，使下一次研究从已知差异继续，而不是重新遍历所有工具或换游戏名再写一份脚本。

## 可执行探测流程

从项目根目录运行只读 [kirikiri_probe.py](../../python/engines/kirikiri_probe.py)：

```text
python -m python.engines.kirikiri_probe "游戏/data.xp3" --members "scenario/*.ks"
python -m python.engines.kirikiri_probe "游戏/data.xp3" --members "scenario/*.ks" --recover-akabei-png
python -m python.engines.kirikiri_probe "游戏/data.xp3" --members "scenario/*.ks" --filter-spec "filter.json" --verify-repack
```

`filter.json` 示例为 `{"algorithm":"akabei","seed":798088789}`。这只是参数文件示例，不能自动用于其他归档。探测器输出 JSON 到 stdout，不新建游戏文件、不执行 EXE/DLL/TJS。默认最多 512 个成员、64 MiB 明文；过量时缩小 `--members` 范围，不无界解压整个资源目录。

Akabei 已知明文恢复只取至多 8 个、不大于 8 MiB 的 PNG：由前四字节求候选种子，再验证完整成员 Adler-32 与 PNG 每块 CRC/布局；至少两个不同明文哈希才报告候选。Akabei 忽略种子最高位，报告采用等价的低 31 位值。工具**不会自动采用**恢复候选；确认报告后将参数显式交给下一次调用。没有可靠已知头或找不到通过完整验证的候选时，检查随包过滤器的适用条件，并从游戏样本继续研究算法和参数，不能把乱码替换或关闭校验当作解决方案。

`--verify-repack` 是归档层测试：按所选过滤器重建新内存归档，然后重新解包、解密并比较所有成员。它不修改文本，不证明对白语义 writer 已实现，更不等于启动器会加载新包。

对已经支持的 SCN，过滤器配置直接接入既有批处理：

```text
python -m python.engines.kirikiri_extract extract "游戏目录" "新的提取目录" --archives data.xp3 --filter-spec filter.json --verify-edits
python -m python.engines.kirikiri_extract pack "提取目录" "新的打包目录"
```

报告保存配置，`pack` 沿用。当前一个调用使用同一过滤器配置；不同归档使用不同配置时分别处理，不能错误混用。独立过滤器 writer 输出标准 File 索引；输入 eliF 若要使用该 writer 必须明确选择 `--output-format plain`。Senren 专用适配器拒绝再叠加这层过滤器。

## 译文回注：优先使用 patch.xp3 增量补丁

`patch.xp3` 是 Kirikiri 游戏常见的译文回注方式：启动时挂载补丁归档，让同名资源覆盖原包中的脚本。完成脚本回填后，优先检查并使用这条路线，不必为了修改少量文本重建整个 `data.xp3`。补丁机制是通用工作流；它是否启用、成员路径和加密要求仍需按目标游戏核对。

1. **确认补丁挂载规则**。检查 `startup.tjs`、初始化脚本及必要的 EXE 启动资源，追踪 `patch.xp3`、`useArchiveIfExists`、`Storages.addAutoPath` 等调用及分支。确认搜索目录、覆盖顺序、是否支持 `patch2.xp3` 等编号，以及是否遇到缺号就停止。不能只因出现字符串便判定会加载，也不要覆盖已有官方补丁。
2. **先完成语义回填，再选择变化成员**。从 `gt_output` 读取译文，按原 manifest 重建 KS/SCN 等资源并校验控制码、指针、长度与非文本结构；与原始资源比较，仅把真正变化的文件加入补丁。归档 writer 不能代替脚本 writer。
3. **优先检查扁平覆盖方式**。常见的 `patch.xp3>` 根目录挂载要求将待覆盖文件直接放在补丁根目录，使用原始 basename 和完整扩展名，不保留 `scenario/`、`scn/` 等目录。若目标明确按完整路径查找，则遵循其路径规则；不同源目录的同名文件不能静默合并。扁平化针对游戏实际使用的名称表，不只是修改解包后的文件路径。
4. **采用目标加载器接受的归档格式**。普通 XP3、带过滤器的 XP3、Cx/Hx 等分别使用对应 writer；支持 XP3 不等于接受任意明文包。EXE 若接管文件系统，须继续追踪其挂载、名称哈希与认证要求。完整脚本包 `scenario.xp3` 不能仅改名就视为正确补丁。
5. **重新读取最终补丁验证**。确认成员集合恰好是变化集合、名称/路径符合覆盖规则、正文等于回填结果；检查全部校验和、加密认证与内层格式。先在新的结果子目录生成 `patch.xp3` 和报告，在用户授权范围内部署到已确认的补丁搜索目录，保留原游戏包。
6. **实机验证覆盖效果**。完全退出进程后重新启动，进入被修改的剧情段落；开场测试优先从新游戏进入，避免旧存档或已缓存脚本影响判断。分别记录“工具验证通过”与“用户/实机确认生效”。不生效时依次核对补丁位置和编号、挂载条件、覆盖优先级、资源名/目录、索引格式、加密认证，再判断外部签名是否相关。

**交付时最后提醒用户**：如果译文在游戏中显示缺字、方框或部分字符空白，考虑替换 `data.xp3` 中游戏实际使用的字体文件，选择覆盖译文所需字符的字体。先确认字体资源和加载方式，再按对应归档的加密、认证与封包流程生成替换补丁或新包，不直接覆盖原始 `data.xp3`。不要把缺字直接判定为文本回注失败。

**Hxv4 的具体实现**见 [扁平补丁流程](hxv4.md#hxv4-扁平-patchxp3)：`build_flat_patch` 保留成员 ID/key/文件名哈希，将目录哈希改为根目录，并生成有效的 Poly1305 索引认证标签。是否需要外部 `.sig` 须按目标加载链路判断。这些密码与哈希细节属于 Hxv4，不能直接套到普通 XP3 或其他过滤器。

现有 `kirikiri_extract pack` / `kirikiri_hxv4_text pack` 提供脚本重建与封包能力，但输出可能包含完整脚本集合、保留原路径。交付增量 `patch.xp3` 时仍需完成上述变化筛选及路径适配；不要虚构尚不存在的 `--patch` 或 `--flatten` 参数。

## 移植契约与优先级

[kirikiri_filters.py](../../python/archives/kirikiri_filters.py) 的 `transform(data, checksum, spec, offset=0, encrypt=False)` 接受明文 Adler-32、成员逻辑偏移和方向。配置只含注册算法名与严格整型参数，拒绝多余字段、布尔值冒充整数和超界值。`StripeCrypt` 的逆变换不同于解密，不能把所有算法默认当成对称 XOR。

[kirikiri_filtered.py](../../python/archives/kirikiri_filtered.py) 负责预算、分段、校验与封包，避免每种算法重复实现 reader/writer。新算法需根据随包实现和样本证据明确状态、整数溢出、偏移、加解密方向和校验阶段，再决定能否放进这个接口；缺少证据时报告未确定的参数或转换，不猜默认值。

后续移植按依赖安排，而不是按用户下一款游戏的名字：

- 可独立的确定性字节过滤器：按覆盖清单补充，先用独立已知向量校准，再测试多段偏移与逆变换。
- 通用 Cx/Hx 家族：先分离控制块、参数包、名称映射与执行模型；不同变体的状态与参数依赖也要核查，不把 Senren 控制块硬套到其他游戏。
- KAG 语义：先以 token 区间记录显示文字、名字属性、ruby、结束/换行控制和分支文字；动态 `&expr`、`%macro` 保留为不可写上下文。标签语义配置不能包含可执行 Python/TJS。未知标签仍保留原文并报告未覆盖，不能默认为对白。
- TJS/加密 PSB：优先获取结构与版本证据，建立独立 parser/writer 验证；不以搜索字符串后原位替换绕过指针与字节码结构。

KAG 的 `[文字'读音]` 中单引号不是属性字符串起点；只有属性赋值位置的引号参与引号匹配。`[[` 为字面左括号。脚本块是原样保留的不透明区段，读取它不意味着运行或分析其业务逻辑。字符偏移与字节偏移必须分开，保留编码、BOM 和 CR/CRLF/重复 CR 的原貌。
