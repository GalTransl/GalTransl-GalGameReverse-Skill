# GxEngine：V3 MWB 字符串与 zlib 包装

## 适用版本
- 对应源码注释 `Engine: GxEngine V3 mwb`。
- 剧本成员后缀为 `.mwb`，不能直接外推为所有 GxEngine 版本。
- 附带 `Astronauts` 工具目录另有 AVGEngineV2 工具，二者不是同一实现。
- `engine.ini` 给出的单游戏样本仅是来源测试说明，不是通用支持证明。
- 本参考不含任何按游戏标题分支的特殊处理。
- MWB 头固定保留 `0x1C` 字节；来源没有通用 magic 检查。
- 因而目录来源、长度和标记结构必须联合判定。
- 文件头可见的名字或后缀不能替代这些校验。

### GXP 归档头（已确认字段与自校验关系）
[gxp.py](../python/archives/gxp.py) 处理外层 `.gxp` 的头部与有界成员读取。
下列字段布局在真实归档上确认，且**两条关系对每个归档都成立**，可直接用作自校验与误识别拒绝：

```text
0x00  char[4] "GXP\0"    0x04  u32 版本        0x08  u32 标记
0x0C  u32 标志0          0x10  u32 标志1       0x14  u32 标志2
0x18  u32 成员数         0x1C  u32 索引区字节数
0x20  u64 数据区字节数   0x28  u64 数据区偏移
0x30..  固定头部，其后为索引区

关系一： data_offset == 0x30 + 索引区前置长度 + index_size
关系二： data_offset + data_size == 文件大小
```

- 两条关系不成立即拒绝该文件，不靠扩展名或目录名判定。
- `read_member()` 要求调用方**从已解码的索引项**给出 `(offset, size)`，
  只做显式边界检查，**绝不通过字节扫描反推**成员位置。
- **数据区在已验证版本中是明文且未压缩**：索引中的大小等于原始成员大小，取出的成员可直接读取。
  压缩或加密必须按版本另行确认后使用，本模块两种情况都不预设。
- 索引项本身的轻度混淆**未在本模块解码**：本模块只暴露已确认的头部关系与有界原始读取接口，
  不再猜测字段宽度或解密无法验证的字节。索引项解码应在方案按版本确认后单独实现。

```python
from python.archives.gxp import read_header, read_member, describe
hdr = read_header(archive_bytes)          # 关系不成立时抛 FormatError
info = describe(archive_bytes)            # 汇总字段，不解码
member = read_member(archive_bytes, offset, size, hdr)   # offset/size 来自索引项
```

## MWB 包装
- [unpack_mwb](../python/engines/gxengine.py#L20) 返回完整解压 payload。
- `LE32[0x14]` 是未压缩大小，`LE32[0x18]` 是存储大小。
- 实际正文从 `0x1C` 开始。
- 两大小不同则执行 zlib 解压；相等时按原始未压缩正文处理。
- 存储大小必须精确等于文件尾正文长度。
- 默认最大输出 64 MiB，可由调用方显式降低或提高预算。
- 解压必须达到 EOF、没有额外尾流、没有超量输出，并精确匹配声明长度。
- 任何不满足的文件直接报错，不沿用源“提示后继续”的宽松行为。

## 混合端序文本记录
- [scan_fields](../python/engines/gxengine.py#L37) 扫描已知六字节标记。
- 预设 pattern 为 `[08/05] 1A 00 00 [00..02] xx`。
- 末四字节其实是**大端**文本 byte_length。
- 因而该 pattern 限制已核实字段长度为 `0..0x2FF`。
- 标记 `08` 与 `05` 不应简单归并成同一语义。
- 源预设提醒 `05` 是控制字符串，可与 `08` 分开提取以免误译。
- Field.kind 保存首字节，让调用方在翻译前显式分类。
- Field.length_offset 指大端长度位置，start/end 指原始正文跨度。
- 扫描完成后所有未命中前缀、间隙和结尾仍留在 payload 中。
- 匹配标记但长度越界时拒绝，而不是把它解释为“没有台词”。
- 编码默认 UTF-8，与源初始化一致；也允许显式指定经过验证的编码。
- 无法解码的候选会报错，不像上游继续跳过造成静默漏提。

### 头部多分区：符号表必须先于字符串判据处理

在已验证版本中，MWB 头部在**文件头之后、代码区之前**还包含按顺序排列的两个分区。
它们是**结构**，不是剧情正文，但位置在正文记录之前，因此分桶/分流必须在字符串级判据之前先识别它们：

| 顺序 | 分区 | 内容 | 判据（不依赖具体数量） |
|---|---|---|---|
| 1 | **符号表** | 以 **`(名称, 所属文件)` 交替**存储的名称 → 定义文件映射 | 相邻两项的偶位是名称、奇位是 `xxx.txt`；**间隔恒为 2** |
| 2 | **指令名表** | 引擎注册的指令名（如 `toint`、`msg.show`、`stand` 等） | 该区段内为纯 ASCII 指令名，且代码区记录会引用它们 |
| 3 | 代码区 | 其余全部记录 | 上述两者之后 |

**为什么必须整体保护**：符号表同时收录三类「按名引用」的名字——脚本块名、变量名、场景/跳转目标。
其中相当一部分含假名或汉字（例如 `VAR_92_ルート選択`）。
**按“含假名/汉字 = 待译”的字面判据会把它们整体误译**，进而使按名引用（条件跳转、数据表匹配）
全部失配 —— 这不是“效果差”，而是“玩不了”。因此分桶流程的**第一步**就应查符号表，命中即 `keep`。

**两条自检判据**（用于确认符号表被正确识别，而非依赖硬编码数量）：
1. `名称 == 文件名去扩展名` 的条目应占相当比例；其余应归入少数共享文件（如 `vars.txt`、`macro.txt`）。
2. 代码区中按名引用的指令，其参数应能命中该表（比例可用作交叉验证）。

**指令名表的一个副作用**：它里面可能**恰好含有与结构标记同名的指令**。
若用“遇 `text` 深度 +1、遇 `endtext` −1”这类栈式配对来切分消息，
深度会因为表内同名项而**永远回不到 0**，导致一条消息都切不出来。
⇒ 消息切分必须改用**相邻配对**（见下文“消息结构”），不要依赖全局深度计数。

## name/message 与控制保护
- 源预设 `名字「正文` 的 name 长度限制为 1 至 10 个字符。
- ASCII-only 字段、开头大写命令或 `@`、包含下划线的字符串可能被跳过。
- 这些是特定提取规则，不意味着所有非 ASCII 字段都适合翻译。
- 本 leaf 返回完整字段，不用猜名结果覆盖结构内变量。
- 建议先按 kind 筛选，再将已确认文本交给 name/message 规则。
- UTF-8 字符数和字节数必须区分，长度字段永远写字节数。
- 控制标签、换行和资源标识的完整性由上层语义策略保护。

### 消息结构（`text` 与 `endtext` 的相邻配对）

要产出 `{"name", "message"}` 这种按“一句话”组织的文件，需先确定消息边界。
在已验证版本中，消息形如：

```text
text                ← 消息开始（指令名本身也是内联字符串记录）
[角色名]             ← 仅角色台词有，旁白没有
[语音档 ID]          ← 可选
「正文第 1 行
　正文第 2 行
…」
endtext             ← 消息结束
```

**切分铁律：只认「`text` 的下一个结构标记就是 `endtext`」的相邻配对。**
- ⚠️ 不要用栈式深度配对：见上文“指令名表的副作用”，表内同名项会让深度恒不为 0。
- **角色名判定的双锚点**（不要靠单一启发式）：
  1. **权威白名单**：引擎自带的数据表（角色定义表，通常为 CP932 表格）是角色名的硬依据；
  2. **语音档 ID 佐证**：形如 `^[a-z]{3}\d{4}$` 的短 ID，前缀为角色缩写，紧跟名字时基本可判为说话者；
  3. 低置信兜底：短串 + 无句读 + 非助词结尾 + 后随引号台词。
- **取舍原则：宁判旁白，不误判名字。** 误判会把正文塞进 `name` 导致内容丢失；
  漏判只是名字混进 `message` 开头，内容不丢、翻译时一并处理即可。
- ⚠️ **语音档 ID 会混进 `message`**，剥离规则应是「形如 `^[a-z]{3}\d{4}$` 的**无条件剥**」。
  若写成“仅当后随引号才剥”，以 `（` 开头的内心独白会漏剥。
- **独立交叉验证**（避免自证）：用**另一处结构**做锚点 —— 立绘类指令（`stand <名字> …`）里的名字集合，
  与解析出的名字集合对比：前者有、后者无 ⇒ 漏判候选；后者有、前者无 ⇒ 临时角色名（杂兵等），合理。
- **完整性自检**：把产出 JSON 反向展开（按 `\n` 拆行）与原码消息区正文行序列**逐条逐序比对**，
  证明“没有漏行、没有错序”。

## 本地回填
- [replace_fields](../python/engines/gxengine.py#L57) 接受字段序号到 str 的映射。
- 它从原文件重新解包和解析，避免对已移位 offset 二次使用。
- 从后往前替换文本与其四字节大端长度，保留所有其他 bytes。
- 译文编码后超过 `0x2FF` 时拒绝，不生成本 reader 无法再读的标记。
- 重组 payload 后重算 MWB 的两个小端大小。
- 默认用 zlib 压缩，也可明确选择不压缩。
- 若压缩后恰好与原始 payload 同长，使用原始 payload 避免大小判定歧义。
- 这里重建的是源代码覆盖的本地字符串布局，不是整个 GxEngine 指令集。
- 若目标版本另有全局跳转/索引，须先补充验证，不能套此 writer。
- 外层容器索引和文件部署由公共层/专用工具另做。

### 回填的三道闸门（缺一不可）

字符串内联存储 ⇒ 改变串长只需重写 4 字节长度前缀。但这**不自动成立**，必须以三道闸门证明：

1. **恒等重建**：用全部原文回填后，产物 SHA-256 必须与原文件一致。
2. **骨架校验**：抽出“记录之外”的全部字节，回填前后**逐字节一致** —— 证明非记录字节零位移。
3. **可逆性**：译文再换回原文后，与原文件字节级相同。

> 判据补充：若文件内确实**不存在**指针表，则未改动区出现“随机 4 字节值恰好等于某偏移”属密度巧合，
> 必须用统计（实际命中率 vs 期望命中率）区分，不能因为“扫到了”就断定有指针表。

三道全过之前，不要进入批量翻译。

## 调用示意
```python
from python.engines import gxengine
payload = gxengine.unpack_mwb(member_bytes)
fields = gxengine.scan_fields(payload)
# 先确认 fields[0].kind 属于需要翻译的文本类型。
result_bytes = gxengine.replace_fields(member_bytes, {0: "译文"})
```
- source member 必须处于原包装状态，不能把 payload 直接当 member_bytes。
- 不依赖 `ExVar`、PyQt5、原 tools 或相对工作目录。

## 验证与阶段缺口
- 合成测试验证大端字段长度与小端包装长度的组合。
- 变长 UTF-8 测试确认前后不透明字节及 zlib 往返。
- 测试覆盖越界标记和超出解压预算的拒绝。
- GXP 头部的两条关系、有界成员读取和坏输入拒绝见 `tests/test_gxp.py`（合成样例）。
- 尚未运行实际游戏或 GxpPacker，也未验证其他 MWB 世代。
- 未实现 GXP 索引项解码与封包、V2 剧本转换、字库扩展和完整控制字段识别。
- 文本解析成功不能替代 UI、分支、存档等部署回归。
